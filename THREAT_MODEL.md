# P.R.I.S.M. threat model (one page)

## Protected assets
1. File contents (confidentiality and integrity).
2. File keys (DEKs) and each device's private keys.
3. The identity directory: users, roles, device status.
4. The audit log (integrity and completeness).

## Attackers considered
- **Thief of a lost device**, holding its private keys but not the owner's other devices.
- **Network attacker** who can read, replay and modify requests (not break TLS or the crypto).
- **Malicious or compromised member** trying to read files outside their ACL or become admin.
- **Insider with database access** trying to edit or delete audit entries.
- **Harvest-now-decrypt-later attacker** who records ciphertext and wrapped keys today.

## Controls
| Threat | Control |
| --- | --- |
| Lost device keeps working | `report_lost` and `revoke_device` take effect on the primary at once and reach every reachable replica: measured at tens of milliseconds across three real node processes on one machine (`python -m kig.netcluster`; one host, one clock, loopback, so not a network measurement), and within the injected 5 to 50 ms delay in the in-process simulation. A replica cut off from the primary can serve for at most one lease (2 s in the real-process harness, 5 s `LEASE_S` in the simulation; a deliberate availability choice) and then refuses everyone. Denied requests raise R1. See docs/REVOCATION.md |
| Old key still decrypts new data | next authorised read rotates to a fresh DEK and epoch; wraps are bound to file, device and epoch |
| Replay and forgery | signature over the whole envelope, 30 s freshness window, per-device nonce, refusal of requests signed before a restart |
| Lockout abuse (DoS by claiming a victim's id) | there are no lockouts: failed authentication raises an alert and is log-bounded, so an attacker cannot lock a victim out, and a client retrying its own envelope is not penalised |
| Privilege escalation | admin-only role changes, last admin cannot be demoted, every promotion alerts (R4) |
| Audit tampering | each entry is hash-chained and signed with ML-DSA; the service refuses to start on a broken chain or when the log is shorter than the number of entries state.json has seen. State is saved after every logged event. This is NOT tamper-evidence for the log tail: someone with write access to the data directory can cut the tail and rebuild `audit.head` and state without any key if they also have the service key, and `audit.head` is only a copy of the last entry. `prism_verify.py` (standalone, no kig code) re-checks the chain and signatures without the service and prints a NOTE, exit code 2, when completeness is not established. The real control is an external head: print `verify-log` output or the backup manifest head after each backup or at shutdown, keep it off the host, and check with `verify-log --expect-head` |
| Quantum adversary | hybrid ML-KEM-768 + X25519 key wrapping, ML-DSA-65 signatures |
| Crash mid-revocation | audit entry is written before state; on restart, removals found in the audit log are re-applied (fails closed) |

## Assumptions
- The service host and its `data/` directory (signing key, operator token) are not compromised.
- Transport is TLS-protected in deployment (the demo binds to localhost).
- Device clocks are within 30 s of the service.
- Libraries are correct: `cryptography` for all encryption, KEM and signatures, and PyCryptodome only for the optional k-of-n split of the backup key. No custom primitives are used.

## Known limits (stated honestly)
- **A revoked device keeps anything it already decrypted or copied.** Rotation protects future versions only.
- **Root of trust.** Every enrolment is signed by an enrolling device, up to a root device (the first admin, or one added by operator recovery). Clients verify that chain and check each recipient key against it, for recipients and for the writer of a file seen for the first time. If the client is given `--root-fingerprint` (printed by `init` and `recover-admin`), a malicious server cannot swap keys or invent files. If it is not given, the client pins the root behind its own enrolment on first use, so a server that controls the very first contact can still substitute a whole directory. Enrolment is also checked by comparing a device fingerprint out of band (`kig enroll --expect-fingerprint`; `--unverified` is recorded as such). A demoted admin stays proven in client pins. Every signer in an enrolment chain must be shown to be an admin (a signed `create_user` or `set_role` request, carried in the directory reply), so a plain member's device cannot add a reader. Clients cannot see revocation: a malicious server can re-list a revoked device with its old valid proof, so recipient choice for new wraps should still be checked against alerts and the audit log. A device enrolled by an admin who was later demoted must be re-enrolled. The directory reply (public keys and signed enrolments) is public data and is served to any authenticated user. Offline recovery adds a root that existing clients must pin (`kig pin-root`).
- **Private keys sit in files** (mode 0600, passphrase-sealed with scrypt + AES-256-GCM when a passphrase is set). `kig/keystore.py` is the interface for a hardware or KMS store, but we ship no such driver. Python cannot wipe memory, so a running process holds its key in RAM.
- **Nonces are kept in memory.** A restart is covered by refusing older timestamps; a multi-node deployment would need a shared store.
- **Metadata is visible to the service:** file ids, ACLs, device ids, access times.
- **Rule-based detection only.** It catches the listed patterns, not novel behaviour. No ML by design.
- **Cluster transport.** The real node processes sync over plain HTTP with a shared cluster token. Across hosts this needs TLS. A holder of the token can make a node serve repeated full snapshots. A node that is restored from an old copy fails closed until it syncs. `docs/REVOCATION.md` lists the tests.
- **Powerful devices.** A limited device (a phone) always acts as a plain member. Removing an admin's device, disabling an admin or changing an admin's role needs another admin whose device is at least 15 minutes old (the service clock; a wrong host clock changes it), and removing an admin's limited device raises alert R5. A stolen full admin device is an admin until the host removes it with `kig revoke-device`. Details and tests: `docs/CORE_HARDENING.md`.
- **Deleted ids.** A deleted file id keeps a small tombstone (capped per owner by `KIG_MAX_DELETED_IDS`, default 2000) so a re-created file is not mistaken for a rollback; only its owner or an admin can create it again.
- **Single-node, single-file-store.** State is one JSON file with atomic replace; throughput and file size (about 5 MB per file, checked on the ciphertext) are prototype-grade.
- **Availability:** a stolen request cannot lock out a victim's device. Nobody is locked out by failures. Valid-signature traffic has a per-device budget (240/min). Failed or unauthenticated requests share a per-source budget (1200/min) and a small pre-auth log budget. Events after a valid signature (revoked device use, replay, stale, wrong audience) are logged per device and never share the anonymous budget. A 10,000 file cap bounds state size. Signature checks still cost CPU, so a distributed flood can slow the service.
- **Behind a proxy:** with `KIG_TRUSTED_PROXY=1` the source is the address the trusted proxy appended (hop `KIG_PROXY_HOPS` from the right, default 1). Never enable it without a proxy that overwrites or appends X-Forwarded-For.
- **Retries:** an identical envelope resent from the same source gets a 409 `replay` with no cached result; the client should build a new envelope.
- **Owner/admin compromise:** a compromised owner or admin device can still overwrite or wipe a file (the previous version is kept for 30 s only). The server cannot verify wraps or ciphertext it is given. `needs_rotation` is serviced only when an owner or admin device holding a wrap fetches the file, and `can_rotate` is supplied by the server, so after a revocation the old key can stay live until then. `rotate-pending` (CLI) walks every flagged file for that purpose. An admin must be in the file's ACL to rotate, so a file whose owner lost every device is unrecoverable by design.
- **Replica restore:** snapshots carry a restore generation and the audit length. Replicas accept a snapshot only if (generation, length) is strictly greater than what they hold, so a primary restored from an older backup converges. Pass `live_dir` to restore so the generation is bumped above the surviving directory's; without it the generation is the larger of the backup's own and the current time in milliseconds, plus one, so repeated restores still advance.
- **Bootstrap crash:** `bootstrap` saves state before it logs, so a crash in between leaves a working directory whose first audit entries (`service.bootstrapped`, `device.enrolled`) may be missing from the log. Nothing else is lost.
- **Proxy:** `KIG_TRUSTED_PROXY=1` is only safe when the service port is reachable only through your proxy; otherwise a client can send its own X-Forwarded-For and pick its source address. `KIG_PROXY_HOPS` must be an integer from 1 to 16 or the service refuses to start.
- **Client trust in the server:** the signed per-version manifest binds file, epoch, ACL, owner and key commitment, and clients require writer authority (the owner, or an admin proven by a signed role request). A malicious server cannot forge a manifest, but it can withhold updates or replay an older signed version unless the client has pinned a newer one.
- **Revoke scope:** any active device of a user can revoke that user's other devices, by design (lost-phone recovery from the laptop). The last active device of the last active admin can never be revoked or reported lost, so a thief holding one device cannot lock the owner out of the admin role; a thief can still revoke the owner's other devices, including the owner's other admin devices. That cannot be prevented without a second person: a delay the target may cancel would let the thief cancel too. What we do is raise a critical alert (R5-ADMIN-DEVICE-REVOKED-BY-SIBLING) and recommend a second admin user, because another admin can remove the thief's device and operator recovery needs only the host. Runbook: on day one enrol a second admin device and, if possible, a second admin user, and keep the operator able to run `recover-admin`. Operator recovery (`recover-admin`, offline, needs the data directory) enrols a fresh admin device; it is logged as an operator action, flags the user's files for re-keying, and does not restore file keys.
- **Rollback of the whole data directory** is detected only against a pin kept outside it (`KIG_PIN_FILE`), which the service refuses to start below. If the variable is set but the file is missing on a non-empty log, the service refuses to start. If the variable is not set at all, there is no rollback protection: a restored older directory starts silently, and the audit log alone cannot show that it is stale.
- **Quotas and sharing:** 1,000 files and 256 MB per owner, 4 GB in total. Only admins add other users to a file's list, so a member cannot plant files in someone else's list; owners and admins can delete files. A deleted file id is never reused (a tombstone is kept), so clients that pinned a later epoch do not mistake a re-created file for a rollback.
- **Single worker:** one process per data directory. A lock file makes a second process refuse to start. `uvicorn --workers N` is not supported.
- **Threshold shares:** a forged share cannot block recovery while k genuine shares are supplied, but the search is bounded, so many forged shares for one index slow it; the share check value is not a MAC.
- **Write roles:** ACL members read. Only the file owner or an admin can write or rotate. Each version carries a key-commitment tag, so a wrong key is rejected rather than decrypting garbage.
- **Backup memory:** blobs are streamed; the sealed metadata (state and audit log) is held in memory, so memory grows with the number of files and audit entries, not with stored bytes. Writes pause while a backup is built. The backup contains client ciphertext, so blob confidentiality rests on the clients' encryption, and the metadata is sealed to the backup key.

## Out of scope, and why

Track 4 lists more topics than one prototype should claim. These are not built, and the prototype makes no claim about them.

- **SLH-DSA.** Signatures use ML-DSA-65 only. One standardized signature scheme is enough for the flows here, and a second one would add code to test without adding a property we claim. Nothing is signed with a hash-based scheme.
- **Double Ratchet, PQXDH and forward secrecy for completed sessions.** This is a key service for shared files, not a messenger. There are no sessions. File keys are wrapped to a device key with a fresh KEM encapsulation per wrap, but a stolen long-term device key still opens every wrap made for that device and any ciphertext the thief holds. We do not claim forward secrecy.
- **End-to-end messages, loss and reordering, delivery failure reports.** Not built, for the same reason: the unit of work is a file version, not a message stream. Duplicate and replayed requests to the service are rejected (nonce, 30 s window, signed audience).
- **Session resumption.** Not supported. Every request is signed on its own, so there is no session identifier that another identity could inherit.
- **Merkle transparency log.** The audit log is a signed hash chain, not a Merkle tree. It proves order and edits inside the log, not completeness, and has no inclusion or consistency proofs for third parties. Keeping an external head (`--expect-head`, `KIG_PIN_FILE`) is how completeness is checked.
- **Graph or ATT&CK style detection, and lateral movement between services.** Detection is five explainable rules over one service's audit events. There is no model of paths between services, so an attacker moving across services with valid credentials is not flagged. The measured recall reflects this (`README.md`, "Detection, measured").
- **Hybrid logical clocks and out-of-order events from different clocks.** Events are ordered by the audit sequence the service assigns, and the rules and cooling-off use the service's own clock. Nodes in this repository share one host and one clock. We do not handle events that arrive from other sources with different clock offsets, and we do not flag uncertain ordering.
